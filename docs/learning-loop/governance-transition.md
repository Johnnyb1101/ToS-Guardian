# Governance transition and separated local controller

`tools/governance-transition.js` prepares an unsigned exact plan and checks an externally supplied owner envelope. Its `valid` result means signature/plan integrity only; it never signs, connects, persists or authorizes a transition. The signature purpose is `tos-guardian.governance-transition.v3` followed by a newline. This envelope cannot pass the ordinary version 2 release gate.

The plan binds the environment/project/service/database destination; current release generation, configuration, head and halted state; governance registry, epoch and head; verifier and migration inventory hashes; old/new release configurations and source manifests; reviewed standard; and independent owner-key fingerprint. Approval lifetime is at most 24 hours. Only the explicit serverPipeline/storageSchema/baselineSchema/migrationManifest policy-version differences are permitted. Lessons, sites, models, prompts, cache and all other settings must remain unchanged. Dot-containing configuration keys cannot create ambiguous difference paths.

`release-control/` implements a separate local authority boundary. Its TLS-verified psql transport accepts only fixed RPCs and an explicit restricted login. The installer pins the owner and reviewer keys externally. PostgreSQL owns atomic state changes and anti-replay enforcement; it does not claim to verify Ed25519 itself. The NOLOGIN owner, restricted controller and ordinary application are distinct database identities. The controller has no direct table writes, ownership or role-administration rights. The forward SQL fences table/column writes and known legacy release/bootstrap RPC overloads while preserving service_role SELECT access to public release data.

The controller verifies measured source/runtime closure and checks the installed catalog through every RPC. Both signed source manifests must include `artifacts/release-build`, binding the complete build artifact's exact bytes and SHA-256. Maintenance evidence must match those artifacts, not merely the same release JSON. Source-list completeness and external native dependencies remain explicit installation review obligations. `installedMigrationManifestHash` means the proxy's complete migration-file inventory; it does not by itself prove installed schema. Control SQL belongs to the verifier closure and installed function definitions belong to the catalog fingerprint.

Adoption and activation are separate transactions. Adoption locks authorization ID, registry and the real active-release row, requires the exact existing unhalted epoch-zero state, records the plan and advances governance only. The active release generation/configuration remain unchanged. Activation requires epoch one, full recomputed maintenance-final evidence, independent owner release/control envelopes, a verified online audit event, and the exact adopted baseline/candidate pair. Publication increments release generation once. SQL rechecks state and expiry under lock; event, consumption and pointer changes are atomic.

An identical committed retry returns the durable result even after expiry; altered content under a consumed authorization ID fails. Precommit failure leaves state unchanged. A restarted compatible controller recovers a lost response using exact replay while retaining epoch and authority separation.

The initial signed plan can declare one exact backup release and build. With the recovery migration installed before adoption, a separate authorization can publish that backup from the exact activated candidate to the next release generation in epoch one. The candidate and backup must share their migration inventory, schema, cache and other policy settings apart from the server pipeline fingerprint. The controller recomputes current-standard evidence for the candidate-to-backup build pair. Bootstrap, legacy activation and application rollback through those older APIs remain fenced.

The forward SQL was generated with `supabase migration new`. The immutable artifact requires explicit expected database, installer/session identity, exact supported server version and independently reviewed preinstallation catalog pins, with no defaults. Host/CA/credential configuration and authorization to install remain separate operator responsibilities; installer pins are not owner release approval. The same SQL bytes are rehearsed locally and may be considered for a later separately approved installation. `tests/release-control-db.test.js` alone enforces the disposable, unique-marker, loopback-only cluster and never accepts a production connection target. It runs original archived release/bootstrap SQL, negative installer-pin tests before DDL, the final forward SQL, independent authenticated LOGIN denial tests, actual TLS transport, ephemeral owner verification, hypothetical signed maintenance evidence acceptance, concurrency, expiry and atomic recovery. These are local contract tests, not real provider evaluation or owner release approval. See `release-control/README.md` for arguments and detailed limitations.

No production schema, credentials, role grants, hosting, owner signatures or deployments changed. Before any production proposal: independently review the live catalog and all privilege/dependency paths; prepare credential retirement and other-consumer impact; install/protect the separate controller and native dependencies; freeze final artifacts; obtain real evaluation/reviewer evidence; and obtain specific approval for actual owner signing, permission changes, cutover and deployment. Paid evaluation needs its own approved spending limit. The administrator/provider and compromised-controller trust boundaries remain explicit.
